# Screen-Off Sleep Alarm

## Enterprise Product Requirements Document (PRD)

**Document Version:** 1.0
**Status:** Product Definition
**Platform:** Android
**Primary Market:** Global, initially India
**Product Type:** Offline-first personal utility
**Primary Function:** Automatically schedule a wake-up alarm based on the user's latest meaningful screen-off event plus a configurable sleep duration.

---

# 1. Executive Summary

Screen-Off Sleep Alarm is an Android application that automatically schedules a wake-up alarm when the user stops using their phone for the night.

The core interaction is:

> **Screen turns off → application records the event → adds the configured sleep duration → schedules an alarm.**

Example:

```text
Screen OFF
11:42 PM

Configured sleep duration
7h 15m

Automatically calculated alarm
6:57 AM
```

When the user turns the screen back on, the application cancels the pending sleep alarm because the previous screen-off period is no longer considered an active sleep session.

When the screen is subsequently turned off again, a new sleep session begins.

The product must be:

* Reliable
* Battery-efficient
* Offline-first
* Privacy-preserving
* Transparent
* Resilient to Android background restrictions
* Compatible with modern Android versions
* Recoverable after device reboot
* Deterministic in its scheduling behavior

The product should not require a backend, account, or continuous internet connection for its core functionality.

---

# 2. Problem Statement

Traditional alarm applications require users to manually choose a clock time.

This creates friction for users whose bedtime varies.

For example:

```text
Monday
Sleep: 11:15 PM
Wake: 6:30 AM

Tuesday
Sleep: 12:05 AM
Wake: 7:20 AM

Wednesday
Sleep: 11:48 PM
Wake: 7:03 AM
```

A fixed alarm requires the user to manually calculate or choose the wake-up time every night.

The proposed product removes this step.

The user specifies:

> "I want approximately 7 hours 15 minutes of sleep."

The application determines the wake-up time automatically based on when the user actually stops using the phone.

---

# 3. Product Vision

Create the simplest reliable mechanism for turning **actual phone usage cessation into an automatically calculated wake-up time**.

The product should eventually become a lightweight sleep-oriented automation platform rather than merely another alarm clock.

Potential future capabilities:

* Sleep duration goals
* Sleep consistency tracking
* Bedtime trends
* Sleep-session analytics
* Smart wake windows
* Wearable integrations
* Digital wellbeing integrations
* Multiple sleep profiles
* Travel/time-zone handling
* Intelligent bedtime reminders

However, these are explicitly outside the initial product scope.

# 4. Goals

## 4.1 Primary Goals

### G1 — Automatic alarm creation

Automatically calculate and schedule an alarm when the user's phone enters a meaningful screen-off state.

### G2 — Zero nightly configuration

Once configured, the user should not need to manually set an alarm every night.

### G3 — Reliable execution

The scheduled alarm should fire at the intended time despite:

* Screen being off
* Device entering Doze mode
* Background app inactivity
* Application process termination
* Device reboot

### G4 — Battery efficiency

The application must not continuously poll device state or run an unnecessary background service.

### G5 — User control

Users must be able to:

* Enable/disable automation
* Configure sleep duration
* Cancel an upcoming alarm
* Snooze
* Stop an alarm
* See the next calculated wake time

### G6 — Privacy

The product should operate entirely on-device for its core functionality.

No account should be required.

No screen content should be collected.

No application usage history should be uploaded.

# 7. Core Product Principle

The application's most important rule is:

> **The latest meaningful screen-off event determines the current sleep session.**

Example:

```text
10:45 PM
Screen OFF
    ↓
10:50 PM
Screen ON
    ↓
Cancel previous session
    ↓
11:20 PM
Screen OFF
    ↓
Start new session
    ↓
+7h15m
    ↓
6:35 AM alarm
```

This prevents short periods of inactivity from incorrectly becoming the user's bedtime.

---

# 8. Terminology

### Screen-Off Event

Android reports that the device screen has turned off.

### Sleep Session

A period beginning with a meaningful screen-off event and ending when the screen is turned on or the alarm fires.

### Active Sleep Session

The most recent screen-off event that has not been invalidated by a subsequent screen-on event.

### Sleep Duration

The amount of time the user wants between screen-off and alarm.

Example:

```text
7h 15m = 435 minutes
```

### Wake Time

The calculated time at which the alarm should fire.

```text
Wake Time = Sleep Session Start + Sleep Duration
```

# 11. Screen-On Behavior

When the user turns the screen on before the alarm:

```text
SCREEN ON
    ↓
Check active sleep session
    ↓
Cancel scheduled alarm
    ↓
Invalidate current session
```

The application should **not** automatically reschedule another alarm from screen-on.

The next screen-off event starts a new session.

---

# 12. Short Screen-Off Sessions

A configurable minimum screen-off threshold should prevent accidental sessions.

Recommended default:

**15 minutes**

Example:

```text
11:00 PM → Screen OFF
11:04 PM → Screen ON
```

This should not be considered bedtime.

Instead:

```text
11:00 PM
Screen OFF

11:04 PM
Screen ON

Session discarded
```

Configurable range:

```text
0 minutes
5 minutes
10 minutes
15 minutes
30 minutes
60 minutes
```

For V1, this can remain an advanced setting.

**7h 15m**

**1h – 24h**

Recommended UI:

```text

      7h 15m

   −          +
```

The application should support:

* Preset durations
* Custom duration
* Minute-level precision

---

## FR-002 — Enable Automatic Alarm

The user must be able to enable/disable the automation.

```text
Automatic Sleep Alarm
        [ ON ]
```

When disabled:

* No new sleep sessions are created
* Existing scheduled alarm should be cancelled

---

## FR-003 — Detect Screen-Off

The application must detect Android's screen-off event.

The implementation should be event-driven rather than polling.

The application must not maintain a continuously running loop solely for screen detection.

---

## FR-004 — Detect Screen-On

The application must detect screen-on events.

A screen-on event invalidates the current sleep session.

---

## FR-005 — Calculate Wake Time

Formula:

```text
wakeTime =
    screenOffTimestamp +
    configuredSleepDuration
```

Example:

```text
Screen off:
23:42:10

Sleep duration:
7h15m

Wake:
06:57:10
```

---

## FR-006 — Schedule Alarm

The application must schedule the wake-up alarm using Android's appropriate exact-alarm mechanism.

The scheduling system must support:

* Device idle state
* Application process termination
* Background execution restrictions

---

## FR-007 — Cancel Alarm

The application must cancel an existing alarm when:

* Screen turns on
* Automation is disabled
* User explicitly cancels
* Sleep duration is changed
* A new valid sleep session replaces the old session

---

## FR-008 — Show Upcoming Alarm

# 16. Reboot Recovery

The application must recover an active sleep session after device reboot where technically possible.

Persist:

```text
sessionId
screenOffTimestamp
scheduledWakeTimestamp
sleepDuration
sessionState
```

After reboot:

```text
BOOT_COMPLETED
      ↓
Load persisted session
      ↓
Check session validity
      ↓
Check current time
      ↓
Recalculate/recover alarm
      ↓
Schedule alarm
```

If the calculated alarm time has already passed, the application should not blindly trigger an obsolete alarm.

Instead, mark the session expired.

# 20. State Machine

The product should be implemented as an explicit state machine.

```text
                 ┌─────────────┐
                 │    IDLE     │
                 └──────┬──────┘
                        │
                   SCREEN_OFF
                        │
                        ▼
              ┌──────────────────┐
              │ SESSION_PENDING  │
              └────────┬─────────┘
                       │
                threshold reached
                       │
                       ▼
              ┌──────────────────┐
              │     ACTIVE       │
              └───────┬──────────┘
                      │
           ┌──────────┴──────────┐
           │                     │
      SCREEN_ON               ALARM
           │                     │
           ▼                     ▼
       CANCELLED             RINGING
                                 │
                         ┌───────┴───────┐
                         │               │
                       STOP            SNOOZE
                         │               │
                         ▼               ▼
                       IDLE          SCHEDULED
```

This explicit state model prevents race conditions and ambiguous behavior.

# 21. Concurrency & Race Conditions

Android events can occur close together.

Example:

```text
SCREEN_OFF
SCREEN_ON
SCREEN_OFF
```

The application must ensure that only the newest valid session owns the alarm.

Every session should have a unique ID.

Example:

```text
Session A
11:00 PM

Session B
11:03 PM
```

When scheduling/cancelling:

```text
Alarm ownership = session ID
```

An old alarm must not be able to overwrite or cancel the newer session's alarm.

---

# 22. Idempotency

Screen events must be processed idempotently.

If the same event is delivered more than once:

```text
SCREEN_OFF
SCREEN_OFF
```

the application must not create two independent alarms.

The scheduler should use deterministic `PendingIntent` identity or explicitly cancel/replace the previous alarm.

---

# 23. Time Handling

All internal timestamps should use absolute timestamps.

Do not calculate sleep duration using formatted strings.

Bad:

```text
"11:45 PM" + "7h15m"
```

Correct:

```text
Instant / epoch timestamp
+
Duration
```

The application should account for:

* Midnight
* Day boundaries
* Time-zone changes
* Daylight-saving transitions
* Manual system clock changes

---

# 24. Time-Zone Changes

If the user travels between time zones while sleeping, the intended behavior should be defined explicitly.

Recommended behavior:

> Preserve the absolute scheduled instant unless the user changes the device clock/time zone before the alarm.

For V1, use Android's wall-clock alarm mechanism and document behavior.

---

# 25. Daylight Saving Time

The system must not assume every day has exactly 24 hours.

The sleep duration is a duration, while the displayed wake time is a local wall-clock representation.

# 27. Architectural Principles

## Event Driven

Use Android system events rather than polling.

## Offline First

No backend dependency.

## Deterministic

Given:

```text
screenOffTime
sleepDuration
```

the wake time should always be deterministic.

## Minimal Runtime Footprint

The app should spend most of its life inactive.

## Failure Resilient

Persist state before scheduling whenever practical.

# 43. Success Criteria

V1 is successful if:

1. A user configures the application once.
2. The user turns the screen off.
3. The application automatically calculates the correct wake time.
4. Android schedules the alarm.
5. The alarm fires at the expected time.
6. Turning the screen on before bedtime cancels the previous session.
7. Turning the screen off again creates a new session.
8. Reboot recovery works.
9. Battery consumption is negligible.
10. No internet connection is required.

---

# 44. Failure Scenarios

## Exact Alarm Access Disabled

Display:

> Automatic alarms require permission to schedule exact alarms. Enable access to ensure your alarm fires at the calculated time.

---

## Notifications Disabled

Display:

> Notifications are disabled. Alarm notifications may not appear correctly.

---

## Device Reboot

Attempt to restore the active session.

---

## System Clock Changed

Recalculate based on persisted session semantics and current system time.

---

## Application Force-Stopped

Android restrictions may prevent receivers from functioning normally.

The application should explain that manually force-stopping the app can prevent automation until it is opened again, where applicable.

---

# 45. Edge Cases

### Midnight

```text
11:55 PM + 7h15m
= 7:10 AM
```

Must work correctly.

### Very Long Duration

24-hour maximum prevents absurd alarm scheduling.

### User Changes Duration During Session

Recommended behavior:

```text
Current session exists
       ↓
User changes 7h15m → 8h
       ↓
Cancel old alarm
       ↓
Recalculate from original screen-off time
       ↓
Schedule new alarm
```

Do not reset bedtime merely because the configuration changed.

---

# 46. Security & Abuse Considerations

The app should not expose an API that allows another application to arbitrarily manipulate alarms.

Receivers should be non-exported where possible.

PendingIntent identities should be deterministic and protected.

The application should not use accessibility services as a workaround for screen-state detection.

| Exact alarm restrictions      | Critical | Permission flow + fallback messaging             |
| Reboot loses alarm            | High     | Persist state + boot recovery                    |
| Duplicate events              | High     | Idempotent state machine                         |
| Battery drain                 | Medium   | Event-driven design                              |
| Clock changes                 | Medium   | Absolute timestamps + validation                 |
| App force-stop                | High     | Document Android behavior                        |
| Alarm delivery limitations    | Critical | Physical-device testing                          |
| Permission denial             | High     | Clear onboarding                                 |
| Incorrect session semantics   | Medium   | Explicit state machine                           |

---

# 53. Product Risks

## Risk 1 — Users don't actually want screen-off automation

The concept is differentiated but niche.

Validate with a prototype before investing heavily.

## Risk 2 — Android OEM fragmentation

This is the largest technical risk.

A feature that works perfectly on a Pixel can behave differently on aggressively optimized OEM devices.

## Risk 3 — False bedtime detection

Users may turn their screen off temporarily.

The minimum-session threshold and explicit session model mitigate this.

## Risk 4 — User expectation of alarm reliability

This is an alarm application. Reliability is not a nice-to-have.

A missed alarm is substantially worse than an ordinary app crash.

---

# 54. Product Principles

### Principle 1 — Reliability over features

A single reliable feature is more valuable than ten unreliable sleep features.

### Principle 2 — No unnecessary background work

Use Android events and scheduled alarms.

### Principle 3 — Local by default

Sleep automation does not need a server.

### Principle 4 — Explain permissions

Never surprise the user with system permission requests.

### Principle 5 — Deterministic behavior

The same inputs should produce the same wake time.

### Principle 6 — Explicit state

Do not build the core logic as scattered callbacks.

### Principle 7 — Fail visibly

If the application cannot guarantee automatic alarm behavior, tell the user.

# 58. Final Product Definition

The product can be summarized in one sentence:

> **A privacy-first Android alarm that automatically calculates your wake-up time from the moment you genuinely stop using your phone.**

The fundamental product loop is:

```text
CONFIGURE ONCE
      ↓
USE PHONE
      ↓
SCREEN OFF
      ↓
+ SLEEP DURATION
      ↓
AUTOMATIC ALARM
      ↓
WAKE UP
```

The key engineering objective is not feature breadth. It is **alarm reliability under real Android operating-system and OEM constraints**.

The correct development order is therefore:

**Core event detection → deterministic state machine → exact alarm scheduling → reboot recovery → OEM reliability testing → polished UI → optional sleep intelligence.**
